Phase 2 — AI Agents Service

Est. ~16 days · Partial parallelization
Goal: Smart scheduling, no-show prediction, chatbot, document analysis, provider-patient matching.
2.1

Scaffold AI Service

  • nest generate app ai_service
  • Add ai_queue to RMQ config
  • Port 3006, add to start:dev:all
  • Module setup with Config, Mongoose, RMQ
2.2

Smart Scheduling Suggestions

StepAction
1Accept { providerId, patientId, preferredDays[], preferredTimeOfDay }
2Analyze past booking patterns → suggest optimal slots
3Consider: buffer times, busy days, patient history
4Return top 3 suggested slots with reasoning
APIPOST /api/v1/ai/suggest-slots
2.3

No-Show Risk Prediction

StepAction
1Rule-based scoring: past no-shows (high), time of day, day of week, booking lead time
2Score range 0–100. Flag ≥ 70 as high risk
3Auto-trigger on booking via RMQ
4High-risk → extra confirmation prompts
APIPOST /api/v1/ai/predict-no-show → { riskScore, riskLevel, factors[] }
2.4

Chatbot (Basic NLP)

StepAction
1Rule-based intent router: parseMessage(text) → { intent, entities }
2Intents: book, cancel, reschedule, availability, faq, contact
3FAQ dataset: common lawyer Q&A (pricing, hours, specializations)
4Context tracking via conversationId
5Optional: OpenAI backend for advanced understanding
APIPOST /api/v1/ai/chat → { reply, suggestedActions[] }
2.5

Document Auto-Classification

StepAction
1Accept raw text or file URL
2Classify: contract, court_filing, affidavit, motion, discovery, other
3Extract: dates, party names, case numbers, monetary amounts
4Optional: OpenAI / local NLP model
APIPOST /api/v1/ai/classify-document → { type, confidence, entities[] }
2.6

Provider-Patient Matching

Phase 3 — Document Service

Est. ~16 days · Tasks 3.5/3.6/3.7 parallelizable
Goal: Full document lifecycle — upload, version, share, OCR, e-sign.
3.1

Scaffold Document Service

  • nest generate app document_service
  • Add document_queue to RMQ config
  • Port 3007, add to start:dev:all
  • Install multer, @types/multer, aws-sdk
3.2

File Upload & Storage

  • Create FileUploadInterceptor using Multer
  • Storage: local ./uploads/ (dev) / S3 (prod, configurable via env)
  • Allowed MIME: PDF, DOC, DOCX, PNG, JPG, TIFF
  • Max file size: 20MB (configurable)
  • UUID filenames, preserve original name in metadata
  • API: POST /api/v1/documents/upload
3.3

3.4

Access Control & Sharing

  • POST /api/v1/documents/:id/share — add { userId, permission }
  • DELETE /api/v1/documents/:id/share/:userId — revoke
  • GET /api/v1/documents/shared-with-me — incoming shared docs
  • Access middleware: owner = full, shared = limited by permission
3.5

Document Templates

  • Template schema: name, category, content ({{variables}}), isActive
  • Admin CRUD for templates
  • POST /api/v1/templates/:id/render — inject variables → rendered document
  • Built-in: retainer agreement, fee agreement, intake form, NDA
3.6

OCR for Scanned Documents

  • Install tesseract.js
  • On image/scanned PDF upload → trigger OCR job
  • Store extracted text in Document.textContent
  • Make text searchable via MongoDB text index
  • API: POST /api/v1/documents/:id/ocr — manual re-OCR
3.7

e-Signature

  • Signature schema: documentId, signerId, type (draw/type), signatureData, signedAt
  • POST /api/v1/documents/:id/sign — capture signature
  • GET /api/v1/documents/:id/signatures — list signatories
  • Embed signature onto PDF via pdf-lib
  • Audit trail: IP, timestamp, user agent

Phase 4 — Analytics Service

Est. ~11 days · Tasks 4.5/4.6 parallelizable
Goal: Dashboards, reports, revenue tracking, provider performance.
4.1

Scaffold Analytics Service

  • nest generate app analytics_service
  • Add analytics_queue to RMQ config
  • Port 3008, add to start:dev:all
  • Module with Mongoose, Config, RMQ
4.2

Revenue Analytics

  • Listen to payment.succeeded RMQ event → update aggregates
  • RevenueSnapshot schema: date, providerId, totalAmount, bookingCount, currency
  • API: GET /api/v1/analytics/revenue?period=&from=&to=&providerId=
  • Returns: { totalRevenue, bookingCount, avgRevenuePerBooking, breakdownByProvider[] }
  • Period-over-period comparison
4.3

Appointment Metrics

  • Listen to appointment.* events → update metrics
  • AppointmentMetrics schema: date, total, confirmed, cancelled, noShow, completed, rescheduled
  • API: GET /api/v1/analytics/appointments — period/provider filters
  • Rates: noShowRate, cancellationRate, completionRate
4.4

Provider Performance

  • Per-provider: totalAppointments, completed, revenue, avgRating, utilizationRate
  • API: GET /api/v1/analytics/providers/:id — single provider
  • API: GET /api/v1/analytics/providers — leaderboard
  • Trends: weekly/monthly change across metrics

CI/CD (GitHub Actions)

name: Deploy

  push:
    branches: [main, develop]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test

  build-and-push:
    needs: [lint, test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker compose -f docker-compose.prod.yml build
      - run: docker push ...

  deploy:
    needs: [build-and-push]
    runs-on: ubuntu-latest
    steps:
      - run: ssh $SERVER "docker compose pull && docker compose up -d"
